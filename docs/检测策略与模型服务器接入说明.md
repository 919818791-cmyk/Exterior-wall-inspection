# 检测策略与模型服务器接入说明

更新时间：2026-10-10。

## 当前已实现

- “检测策略”为通用快速体验及五种专业墙面的检测单项、组合项独立绑定 YOLO、云端 API 或本地视觉大模型。组合不读取单项绑定，未配置时直接报错。
- 云端和本地视觉服务按绑定的地址、服务模型名称调用 OpenAI 兼容 `/chat/completions`，原有切片、坐标转换、去重和用量记录继续使用。
- 模型管理维护多个视觉服务配置；API Key 仅引用后端环境变量名称，不在数据库或前端保存密钥。
- “照片相关性判断”也通过相同控件绑定模型，默认预置的照片预检模型继承服务器原有配置：云端为 Qwen3-VL-Flash，本地服务使用已有 `PHOTO_GUARD_MODEL` 和地址。上传预检及健康检查读取此策略；已有预检结果保留原模型记录，新上传照片使用当前绑定。
- YOLO 模型管理维护名称、说明及独立权重版本，不再配置适用墙面和支持的检测类型；每条策略均可选择任意已有 YOLO 模型，并指定具体权重版本；各版本独立启停，允许同时运行多个版本。保存时检查模型存在及版本归属，删除时保护已有引用。
- 本地视觉模型手动启停接口复用既有 Linux vLLM 生命周期管理。每个新增模型有独立 PID、日志目录；策略保存、推理设置保存和后端重启不会启停模型。
- 正式任务保存本次策略快照；修改配置不会改变已排队任务的模型、地址、提示词和并发。
- Windows 当前环境只保存本地配置，启停按钮禁用。尚未接入 YOLO 实际运行，检测时明确返回 409。

## 部署已有功能

在服务器后端目录使用已有 Python 环境执行：

```sh
alembic upgrade head
```

0063 移除同模型版本互斥约束，将已有 YOLO 的跟随绑定固定到原选定版本；原来未选定权重的绑定需手动选择版本。历史选定标记不会作为运行状态，升级不会启动模型。

0062 保留旧提示词和旧权重路径，将原全局模型选择写入各条策略。历史模型墙面、缺陷类型记录保留，但不再参与筛选或校验，无需重新勾选或迁移权重；上线后按训练范围在“检测策略”中绑定具体模型。饰面板新增“面板破损 + 脱落”独立组合，首次保存策略后持久化其绑定。

云端 API：在“模型管理 → 云端 API”新增配置，填写显示名称和密钥变量名，例如 `WALL_VISION_API_KEY`。服务中的模型名称由服务器的 `QWEN_MODEL` 提供，服务地址由服务器的 `QWEN_API_BASE_URL` 提供（到 `/v1`，不要带 `/chat/completions`）。将对应密钥写入后端已有 `.env.local`，按部署方式重启后端，再到“检测策略”绑定。预置通义千问继续使用 `DASHSCOPE_API_KEY`、`QWEN_API_BASE_URL`、`QWEN_MODEL`。

服务和模型必须支持图像输入，提示词须要求只返回 JSON 数组，每项包含 `type`、`confidence`、`bbox=[x1,y1,x2,y2]` 和最多 20 字的 `description`；坐标采用当前解析器约定的 0–999 归一化坐标。配置任意地址不等于支持该供应商的所有返回格式，需要用实际样本确认。

“照片相关性判断”返回 JSON 对象 `{"category":"BUILDING"}` 或 `{"category":"OTHER"}`。已有 Linux 本地 Flash 部署保留 `PHOTO_GUARD_PROVIDER=openai_compatible`、`PHOTO_GUARD_API_BASE_URL`、`PHOTO_GUARD_MODEL` 和可选密钥，策略未手动绑定时自动显示该配置；不用改成默认本地 32B 模型。需要更换服务时在模型管理新增或编辑配置，再在该项中选择并保存。此项绑定 YOLO 时同样可以保存，但尚未接入运行适配，上传预检会明确记为服务失败，不自动改用云端 Flash。

本地服务若已由独立容器或进程管理，在服务器配置 `LOCAL_QWEN_API_BASE_URL`，在服务器配置 `LOCAL_QWEN_MODEL`，在“视觉大模型”Tab 填写显示名称并绑定策略，保留 `LOCAL_QWEN_CONTROL_ENABLED=false`。界面本地启停不可用不影响调用已经启动且可访问的服务。

## Linux GPU 服务器上的本地视觉模型验收

1. 确认目标服务器、驱动、CUDA、vLLM 环境和模型文件可用；这些依赖未在本次 Windows 环境安装或验证。
2. 后端拥有本机模型进程时，配置 `LOCAL_QWEN_CONTROL_ENABLED=true`、`LOCAL_QWEN_VLLM_EXECUTABLE` 及 `.env.example` 中已有显卡、并行数、显存和上下文参数。多模型共享这些启动参数，按实际显存确定同时运行数量。
3. 模型管理中设置模型目录；服务模型名称和不同的本机端口由服务器配置维护。新增模型的目录必须明确填写；预置本地模型可沿用 `LOCAL_QWEN_MODEL_PATH`。管理器控制的是后端同机 Linux 进程，不能远程启停其他服务器进程。
4. 点击“启动”，观察“正在启动 → 运行中”及健康检查；失败时查看日志。停止后检查模型进程及 GPU 占用释放。不要停止正在执行任务使用的服务。
5. 为单项及组合项分别绑定并检测可见光、热成像样本，验证结果归档、模型追溯和并发限制。停止后再修改本地模型配置。

默认日志 `.runtime/local-qwen.log`；新增模型为 `.runtime/vision-<模型 ID>/local-qwen.log`。配置 `LOCAL_QWEN_RUNTIME_DIR` 时以上路径位于该目录下。

## 仍需开发和验收的 YOLO 运行部分

当前只完成权重及绑定管理，以下工作需在具备模型运行条件的服务器继续：

1. 按策略中的模型 ID 和具体版本 ID 从 MinIO 获取权重，校验 SHA-256 后缓存，并将该版本写入任务快照。不要依检测类型查找权重。
2. 实现按版本 ID 隔离的进程或服务管理、端口和健康状态，接入 `backend/app/services/yolo_runtime.py` 的 `version_status` / `control_version`。接口为 `/api/yolo-models/<模型 ID>/versions/<版本 ID>/runtime/start|stop`；启动或停止一个版本不能修改其他版本状态。页面读取每个版本的真实状态和 `control_supported`，接入后启用按钮。
3. 为 `backend/app/services/detection_strategies.py` 的 YOLO 分支实现执行适配器，统一返回缺陷类型、置信度、像素 bbox、图片尺寸和实际模型/版本标识。只保留该策略要求的类型；为不同训练模型明确类名到平台缺陷枚举的映射。
4. 支持任务快照恢复、超时、失败状态、多版本并行运行和旧权重缓存回收；测试单模型覆盖多类型、组合专项模型以及云端/本地服务同时使用。
5. 验证真实 GPU 推理、训练模型检测效果及显存资源释放。当前 `ALGORITHM_INFERENCE_URL` 的历史适配层不会自动执行新模型目录中的任意权重。

本次验证使用模拟 HTTP 服务和浏览器接口数据，覆盖配置与真实图片处理调用链；未验证真实云端供应商推理效果、GPU 推理或 vLLM 进程启动。
