# 检测策略与模型服务器接入说明

更新时间：2026-10-12。

## 当前已实现

- “检测策略”为通用快速体验及五种专业墙面的检测单项、组合项独立绑定 YOLO、云端 API 或本地视觉大模型。组合不读取单项绑定，未配置时直接报错。
- 云端和本地视觉服务按绑定的地址、服务模型名称调用 OpenAI 兼容 `/chat/completions`，原有切片、坐标转换、去重和用量记录继续使用。
- 模型管理维护多个视觉服务配置；API Key 仅引用后端环境变量名称，不在数据库或前端保存密钥。
- “照片相关性判断”也通过相同控件绑定模型，默认预置的照片预检模型继承服务器原有配置：云端为 Qwen3-VL-Flash，本地服务使用已有 `PHOTO_GUARD_MODEL` 和地址。上传预检及健康检查读取此策略；已有预检结果保留原模型记录，新上传照片使用当前绑定。
- YOLO 模型管理维护名称、说明及独立权重版本，不再配置适用墙面和支持的检测类型；每条策略均可选择任意已有 YOLO 模型，并指定具体权重版本；各版本独立启停，允许同时运行多个版本。保存时检查模型存在及版本归属，删除时保护已有引用。
- 本地视觉模型手动启停接口复用既有 Linux vLLM 生命周期管理。每个新增模型有独立 PID、日志目录；策略保存、推理设置保存和后端重启不会启停模型。
- 正式任务保存本次策略快照；修改配置不会改变已排队任务的模型、地址、提示词和并发。
- Windows 当前环境只保存本地配置，启停按钮禁用。Linux 已支持 YOLO 版本独立运行及策略推理调用；指定版本未就绪时返回其实际状态，就绪后按所选类别执行检测。

## 部署已有功能

在服务器后端目录使用已有 Python 环境执行：

```sh
alembic upgrade head
```

0063 移除同模型版本互斥约束，将已有 YOLO 的跟随绑定固定到原选定版本；原来未选定权重的绑定需手动选择版本。历史选定标记不会作为运行状态，升级不会启动模型。

0062 保留旧提示词和旧权重路径，将原全局模型选择写入各条策略。历史模型墙面、缺陷类型记录保留，但不再参与筛选或校验，无需重新勾选或迁移权重；上线后按训练范围在“检测策略”中绑定具体模型。饰面板新增“面板破损 + 脱落”独立组合，首次保存策略后持久化其绑定。

云端 API：在“模型管理 → 云端 API”新增配置，填写显示名称和密钥变量名，例如 `WALL_VISION_API_KEY`。服务中的模型名称由服务器的 `QWEN_MODEL` 提供，服务地址由服务器的 `QWEN_API_BASE_URL` 提供（到 `/v1`，不要带 `/chat/completions`）。将对应密钥写入后端已有 `.env.local`，按部署方式重启后端，再到“检测策略”绑定。预置通义千问继续使用 `DASHSCOPE_API_KEY`、`QWEN_API_BASE_URL`、`QWEN_MODEL`。

服务和模型必须支持图像输入，提示词须要求只返回 JSON 数组，每项包含 `type`、`confidence`、`bbox=[x1,y1,x2,y2]` 和最多 20 字的 `description`；坐标采用当前解析器约定的 0–999 归一化坐标。配置任意地址不等于支持该供应商的所有返回格式，需要用实际样本确认。

“照片相关性判断”返回 JSON 对象 `{"category":"BUILDING"}` 或 `{"category":"OTHER"}`。已有 Linux 本地 Flash 部署保留 `PHOTO_GUARD_PROVIDER=openai_compatible`、`PHOTO_GUARD_API_BASE_URL`、`PHOTO_GUARD_MODEL` 和可选密钥，策略未手动绑定时自动显示该配置；不用改成默认本地 32B 模型。需要更换服务时在模型管理新增或编辑配置，再在该项中选择并保存。此项绑定 YOLO 时同样可以保存，但尚未接入运行适配，上传预检会明确记为服务失败，不自动改用云端 Flash。

本机独立 systemd 用户服务管理照片预检时，设置 `PHOTO_GUARD_SYSTEMD_USER_SERVICE=building-photo-guard.service`。预置照片预检模型的地址和服务模型名称须与 `PHOTO_GUARD_*` 环境配置一致；模型管理直接读取该服务状态并通过 `systemctl --user` 启停，保留其独立显卡和显存参数。后端重启不会重启模型服务。本机已登记 Qwen3-VL-2B FP8（9006，照片预检）、Qwen3-VL-32B FP8（9005，按需启动）和云端 Qwen3-VL-Plus；普通检测策略继续使用原先云端模型。

本地服务若已由独立容器或进程管理，在服务器配置 `LOCAL_QWEN_API_BASE_URL`，在服务器配置 `LOCAL_QWEN_MODEL`，在“视觉大模型”Tab 填写显示名称并绑定策略，保留 `LOCAL_QWEN_CONTROL_ENABLED=false`。界面本地启停不可用不影响调用已经启动且可访问的服务。

## Linux GPU 服务器上的本地视觉模型验收

1. 确认目标服务器、驱动、CUDA、vLLM 环境和模型文件可用；这些依赖未在本次 Windows 环境安装或验证。
2. 后端拥有本机模型进程时，配置 `LOCAL_QWEN_CONTROL_ENABLED=true`、`LOCAL_QWEN_VLLM_EXECUTABLE` 及 `.env.example` 中已有显卡、并行数、显存和上下文参数。多模型共享这些启动参数，按实际显存确定同时运行数量。
3. 模型管理中设置模型目录；服务模型名称和不同的本机端口由服务器配置维护。新增模型的目录必须明确填写；预置本地模型可沿用 `LOCAL_QWEN_MODEL_PATH`。管理器控制的是后端同机 Linux 进程，不能远程启停其他服务器进程。
4. 点击“启动”，观察“正在启动 → 运行中”及健康检查；失败时查看日志。停止后检查模型进程及 GPU 占用释放。不要停止正在执行任务使用的服务。
5. 为单项及组合项分别绑定并检测可见光、热成像样本，验证结果归档、模型追溯和并发限制。停止后再修改本地模型配置。

默认日志 `.runtime/local-qwen.log`；新增模型为 `.runtime/vision-<模型 ID>/local-qwen.log`。配置 `LOCAL_QWEN_RUNTIME_DIR` 时以上路径位于该目录下。

## YOLO 运行服务及检测执行

Linux 已支持上传权重按版本启动和停止。启用 `YOLO_RUNTIME_ENABLED=true` 后，`backend/app/services/yolo_runtime.py` 为每个版本创建独立 Docker GPU 容器，校验 MinIO 权重 SHA256，并通过 `algorithm-model/version_server.py` 加载和预热模型。容器只发布本机回环端口，健康响应须匹配版本 ID、权重 SHA256 且 `ready=true` 才显示“运行中”。默认设备 `cuda:0`，默认镜像 `building-exterior-algorithm-model:cuda`；后端用户需有 Docker 权限。`/predict` 返回原始训练类别、置信度和像素 bbox。启动或停止不改变检测策略绑定。策略执行器通过 `yolo_inference.py` 调用所选权重服务，模型 ID、版本 ID、版本号和 SHA256 均须与响应一致。

版本独立服务的 `/predict` 必须携带表单字段 `models`，值为非空 JSON 数组，例如 `models=["crack"]`。服务依据当前权重的 `model.names` 将所选类型映射为真实类别 ID，传入 YOLO 的 `classes` 参数，并再次过滤返回框。即使权重同时包含 `crack`、`spalling` 和其他类别，只选裂缝时也只返回裂缝；没有裂缝则返回空 `detections`。响应保留原始 `class_id`、`class_name`，新增平台类别 `type` 及 `requested_models`、`executed_models`。支持平台枚举和代码中明确定义的中英文别名；未知训练标签不会按类别序号猜测。缺少字段、空数组、无效格式、不支持的类型或权重缺少任一所选类别均返回 422，不回退为全类别检测。模型尚未就绪返回 503。调用旧版无类别限制接口的客户端须补传 `models`；已运行的版本容器需重启进程才能加载这次修改。

检测策略执行器也按该策略的 `defect_types` 过滤结果，正式任务保存原始输出和缺陷记录前继续按用户所选类型过滤。YOLO 适配复用视觉模型的图片预算校验、EXIF 方向处理、切片生产、原图坐标恢复和跨切片去重，保留原始 `class_id`、`class_name`。HTTP 请求设置超时；服务缺少所选类别时直接显示错误，不调用其他模型。历史 `algorithm-model/server.py` 的结果转换只接受可识别且与目标类型一致的类别，不再把缺少类别信息的框直接标记为目标缺陷。

当前运行的 V1 权重上传文件名为 `best.pt`，通过版本登记 SHA256 和 `/health` 确认训练类别为 `0=crack`、`1=leakage`、`2=abscision`、`3=corrosion`、`4=bulge`。版本服务将 `abscision` 映射为平台的 `spalling`，因此此权重只选裂缝使用 `classes=[0]`，只选剥落使用 `classes=[2]`。返回的剥落 `class_id` 保留原始编号 2，不转换为 1。此编号仅适用于该权重，其他权重仍按实际 `model.names` 解析。

已完成权重缓存、校验、版本隔离、启停、健康检查及快速体验/专业检测策略调用。正式任务快照保存固定模型 ID、版本 ID、SHA256、超时和并发；排队期间修改策略不会切换已有任务的权重，执行时根据容器重新解析端口。旧权重缓存回收及更多真实模型的检测效果、显存资源释放仍需验证。当前 `ALGORITHM_INFERENCE_URL` 的历史适配层不会自动执行新模型目录中的任意权重。

服务器升级内核后，若 Docker 错误包含 `nvml error: driver not loaded`，模型管理会明确显示 NVIDIA 驱动未加载。需为正在运行的内核安装匹配的 NVIDIA 模块，确认宿主机 `nvidia-smi` 正常后再启动模型版本；仅刷新网页或重启后端不能恢复 GPU。

配置与视觉模型调用链使用模拟 HTTP 服务和浏览器接口数据验证；BEST/V1 已在 RTX 5090 上完成真实 CUDA 加载、预热及 8000×4500 图片推理，返回 3 个检测框。尚未验证真实云端供应商推理效果或 vLLM 进程启动。
