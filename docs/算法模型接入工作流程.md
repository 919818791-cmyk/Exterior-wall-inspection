# 算法模型接入工作流程

本文档说明当前仓库中 `wall-crack` 和 `missing` 两个 YOLO 模型是如何接入系统的，重点解释技术实现、接口格式、数据流转和后续扩展方式。

当前已经接入的模型如下：

| 模型文件 | 系统缺陷类型 | 页面展示名称 | 说明 |
| --- | --- | --- | --- |
| `models/wall_crack_yolo11x.pt` | `crack` | 裂缝 | 文档里也称 `wall-crack` 模型，代码内部统一归一化为 `crack` |
| `models/missing.pt` | `missing` | 面砖剥落 | 面砖缺失、瓷砖剥落等别名会归一化为 `missing` |

当前接入分成两条链路：

1. `/trial` 简易 AI 检测体验已经直接调用真实模型服务，用于快速上传图片、推理、返回检测框。
2. 正式项目检测任务保留 `algorithm-worker` 适配层，代码已经支持 `WORKER_MODE=real` 调真实模型；默认配置仍是 `WORKER_MODE=mock`，正式启用前还需要端到端验收。

## 1. 总体架构

真实模型不放在 Web 后端进程里，而是放在独立的 `algorithm-model` 服务中。

先把三个角色分清楚：

| 角色 | 对应目录/服务 | 主要职责 | 是否直接跑模型 |
| --- | --- | --- | --- |
| 前端 | `frontend/` | 上传图片、选择模型、展示检测框和报告 | 否 |
| Web 后端 | `backend/` | 用户鉴权、项目管理、任务创建、MinIO 读写、结果落库 | trial 链路会直接调模型；正式任务链路不直接跑模型 |
| Worker | `algorithm-worker/` | 领取正式检测任务、下载图片、调用模型、回传结果 | 不跑模型，只调用模型服务 |
| 模型服务 | `algorithm-model/` | 加载 YOLO 权重并提供 `/predict` 推理接口 | 是 |

容易混淆的一点是：正式任务里的 `algorithm-worker` 不是 Web 后端的一部分，也不是后端进程里的一个线程。它是算法侧独立进程或独立容器，通过后端开放的 Worker API 领取任务，再通过内部模型 API 调用 `algorithm-model`。

```text
前端 /trial
  -> 后端 /api/trial/generate
  -> 后端读取上传图片或 MinIO 图片字节
  -> POST algorithm-model /predict
  -> 后端把 detections 转成 trial findings
  -> 前端按 bbox 叠框展示
```

正式项目任务链路是另一条路径：

```text
前端创建项目、上传照片、选择检测模型
  -> 后端创建 detection_task
  -> algorithm-worker 领取任务
  -> worker 使用 MinIO 预签名 URL 下载图片
  -> worker POST algorithm-model /predict
  -> worker 转换结果并回传后端
  -> 后端写入 ai_detection_result，项目进入待审核
```

### 1.1 谁连接谁

当前代码里有两种连接方式。

第一种是 `/trial` 简易体验：

```text
浏览器
  -> Web 后端 /api/trial/generate
  -> Web 后端直接请求模型服务 /predict
  -> Web 后端返回简易检测结果
```

这条链路为了让用户快速试用，所以后端直接调用模型服务。对应配置是：

```env
TRIAL_ALGORITHM_INFERENCE_URL=http://localhost:9004
```

这里的 `localhost:9004` 是宿主机访问模型容器的端口映射。`algorithm-model` 容器内部实际监听的是 `9002`，Compose 把它映射到了宿主机 `9004`。

第二种是正式项目检测：

```text
Web 后端
  -> 只创建任务，不直接调用模型

algorithm-worker
  -> 请求 Web 后端 /api/algorithm/tasks/next 领取任务
  -> 下载任务图片
  -> 请求 algorithm-model /predict 做推理
  -> 请求 Web 后端 /api/algorithm/tasks/{task_id}/results 回传结果
```

正式任务里模型调用发生在 Worker 里，不发生在 Web 后端里。对应配置是：

```env
WORKER_MODE=real
ALGORITHM_INFERENCE_URL=http://algorithm-model:9002
```

这里的 `algorithm-model:9002` 是 Docker 内部网络地址：

- `algorithm-model` 是 `docker-compose.yml` 里的服务名。
- `9002` 是模型服务容器内部端口。
- 这个地址通常只给同一个 Docker 网络里的 `algorithm-worker` 调用。
- 普通浏览器、外部用户和公网不应该直接访问这个地址。

如果 Worker 不是跑在 Docker 容器里，而是直接跑在宿主机上，就不能使用 `algorithm-model:9002`，要改成宿主机端口：

```env
ALGORITHM_INFERENCE_URL=http://localhost:9004
```

这样拆分的原因是：

- Web 后端只负责业务、鉴权、任务状态和数据落库。
- `algorithm-worker` 负责和后端任务 API 通信，持有 Worker Token。
- `algorithm-model` 只负责推理，不持有数据库连接、MinIO 写入密钥或 Worker Token。
- 模型服务可以单独配置 GPU、CUDA、PyTorch、Ultralytics 和权重挂载。

## 2. 模型服务如何实现

模型服务代码位于：

```text
algorithm-model/server.py
algorithm-model/Dockerfile
algorithm-model/verify_environment.py
algorithm-model/requirements.txt
```

### 2.1 容器环境

`algorithm-model/Dockerfile` 做了几件事：

1. 使用 Python 3.12 slim 镜像作为基础镜像。
2. 安装运行 YOLO 所需的系统库，例如 `libglib2.0-0`、`libgomp1`。
3. 根据 `PYTORCH_INDEX_URL` 安装 `torch` 和 `torchvision`。
4. 安装 `requirements.txt` 中的 FastAPI、Uvicorn、Pillow、Ultralytics 等依赖。
5. 启动命令为：

```bash
python -m uvicorn server:app --host 0.0.0.0 --port 9002
```

默认 GPU 构建使用 CUDA 12.6 PyTorch wheel：

```env
PYTORCH_INDEX_URL=https://download.pytorch.org/whl/cu126
```

如果只是 CPU 验证，可以改成：

```env
PYTORCH_INDEX_URL=https://download.pytorch.org/whl/cpu
MODEL_DEVICE=cpu
```

### 2.2 权重路径

`docker-compose.yml` 将宿主机 `./models` 只读挂载到容器内 `/models`：

```yaml
volumes:
  - ${MODEL_DIR:-./models}:/models:ro
```

当前两个权重的默认容器路径是：

```env
CRACK_MODEL_WEIGHTS_PATH=/models/wall_crack_yolo11x.pt
MISSING_MODEL_WEIGHTS_PATH=/models/missing.pt
```

代码里还有一个扩展入口 `MODEL_WEIGHTS_CONFIG`，可以用 JSON 配置更多类型或覆盖路径。没有配置时，服务使用上面的两个默认路径。

### 2.3 类型和别名归一化

模型服务内部只认系统缺陷类型：

```text
crack
missing
```

为了兼容不同模型文件里的类别名，`server.py` 定义了别名映射。常见输入会被归一化：

| 输入值 | 归一化后 |
| --- | --- |
| `wall_crack` | `crack` |
| `wall-crack` | `crack` |
| `裂缝` | `crack` |
| `开裂` | `crack` |
| `tile_missing` | `missing` |
| `tile-missing` | `missing` |
| `面砖剥落` | `missing` |
| `瓷砖剥落` | `missing` |
| `面砖缺失` | `missing` |

这里的别名主要用于解析请求参数、权重配置、`/metadata` 中的类别展示，以及推理结果的 YOLO class name 归一化。实际推理时仍按“一类缺陷一个权重”执行；但结果转换会读取每个 bbox 的 `box.cls` 和模型 `names`，只有归一化后的类别与当前执行的系统缺陷类型一致时才保留。例如执行 `missing` 权重时，只保留类别为 `missing` 的 bbox，避免多类别权重中的 `crack`、`other` 等结果被误标为面砖剥落。

### 2.4 模型加载方式

模型不是服务启动时立即加载，而是在需要时懒加载：

```text
第一次请求 crack -> 加载 wall_crack_yolo11x.pt -> 缓存在 _models["crack"]
第一次请求 missing -> 加载 missing.pt -> 缓存在 _models["missing"]
后续请求复用内存里的 YOLO 对象
```

实现要点：

- `_models` 是进程内缓存，避免每次请求重复加载权重。
- `_model_lock` 用于防止并发请求时重复加载同一个模型。
- `_load_model(defect_type)` 会先检查权重文件是否存在，再执行 `YOLO(str(path))`。
- `/ready` 会调用带 `load=True` 的元数据检查，因此它不只是检查路径，还会尝试实际加载模型。

## 3. 模型服务接口

`algorithm-model` 提供 4 个接口。

### 3.1 `GET /health`

用途：快速检查服务是否启动、PyTorch 是否可用、CUDA 是否可见。

返回信息包括：

```text
status
torch_version
cuda.available
cuda.device_count
model_device
predict_device
model_version
models.<type>.weights_exists
models.<type>.loaded
```

`/health` 不强制加载权重，适合轻量健康检查。

### 3.2 `GET /ready`

用途：验收模型是否真的可用于推理。

`/ready` 会尝试加载权重，并返回：

```json
{
  "ready": true,
  "model_version": "trial-crack-missing-v1",
  "models": {
    "crack": {
      "label": "裂缝",
      "weights_path": "/models/wall_crack_yolo11x.pt",
      "weights_exists": true,
      "loaded": false
    },
    "missing": {
      "label": "面砖剥落",
      "weights_path": "/models/missing.pt",
      "weights_exists": true,
      "loaded": false
    }
  }
}
```

如果 `ready: false`，通常是权重路径错误、文件未挂载、模型无法被 Ultralytics 加载，或者 CUDA/PyTorch 环境不匹配。注意：`loaded` 字段表示生成 metadata 时该模型是否已经在缓存里；第一次调用 `/ready` 时即使本次已经成功加载，响应里的 `loaded` 也可能仍显示为 `false`，第二次调用通常会变为 `true`。验收时以 `ready: true`、`weights_exists: true` 和无加载错误为准。

### 3.3 `GET /metadata`

用途：查看模型类别信息。

该接口会加载模型，并返回模型原始 `class_names` 以及归一化后的 `normalized_classes`。如果需要检查权重里 class id 和系统枚举是否对应，优先看这个接口。

### 3.4 `POST /predict`

用途：对单张图片做真实推理。

请求格式是 `multipart/form-data`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `file` | 文件 | 是 | 图片文件，服务端用 Pillow 打开并转成 RGB |
| `models` | 字符串 | 否 | JSON 数组或逗号分隔字符串，例如 `["crack","missing"]` |
| `high_precision` | 布尔 | 否 | 是否使用高精度图片尺寸，目前默认尺寸和高精度尺寸都配置为 1280 |

示例：

```bash
curl -X POST http://localhost:9004/predict \
  -F 'models=["crack","missing"]' \
  -F 'high_precision=false' \
  -F 'file=@/path/to/photo.jpg'
```

推理流程如下：

1. 读取上传文件字节。
2. 用 Pillow 打开图片并转成 RGB。
3. 解析 `models` 字段，把中文、别名、旧名称统一成系统类型。
4. 根据请求模型和已配置权重决定要执行哪些模型。
5. 根据 `high_precision` 选择 `MODEL_IMAGE_SIZE` 或 `MODEL_HIGH_PRECISION_IMAGE_SIZE`。
6. 按顺序执行 `crack`、`missing` 两个 YOLO 模型。
7. 调用 `model.predict(source=image, conf=..., imgsz=..., device=..., verbose=False)`。
8. 将 YOLO 的 `xyxy` 坐标转换为系统使用的 bbox。
9. 过滤低于 `MODEL_CONFIDENCE_THRESHOLD` 的检测结果。
10. 返回统一 JSON。

当前模型服务保留基础推理阈值 `MODEL_CONFIDENCE_THRESHOLD=0.25`，用于让 `/predict` 保留相对完整的模型原始输出，方便调试和后续阈值评估。业务展示和正式落库的阈值由 Web 后端统一控制：置信度小于 `0.6` 的结果不会返回给 trial 前端，也不会写入正式任务的 `AiDetectionResult`。

返回示例：

```json
{
  "model_version": "trial-crack-missing-v1",
  "filename": "photo.jpg",
  "image": {
    "width": 1920,
    "height": 1080
  },
  "requested_models": ["crack", "missing"],
  "executed_models": ["crack", "missing"],
  "detections": [
    {
      "id": "crack-1",
      "type": "crack",
      "type_name": "裂缝",
      "confidence": 0.91,
      "bbox": {
        "x": 120.0,
        "y": 80.0,
        "width": 260.0,
        "height": 140.0
      },
      "mask": null,
      "severity": null,
      "description": "疑似裂缝。"
    }
  ]
}
```

坐标说明：

- YOLO 原始输出是 `xyxy`：左上角 `(x1, y1)`、右下角 `(x2, y2)`。
- 系统统一转换成 `bbox`：`x`、`y`、`width`、`height`。
- bbox 坐标基于原图尺寸，不是前端显示尺寸。
- 前端叠框时使用 `image.width`、`image.height` 做比例换算。

## 4. `/trial` 简易体验如何调用模型

简易体验的后端实现位于：

```text
backend/app/api/reports.py
```

核心路径是：

```text
POST /api/trial/generate
```

### 4.1 图片来源

当前 trial 支持两种来源：

1. 表单里直接带上传文件。
2. 先上传到 quick detection，再通过 `photo_ids` 生成结果。

对第二种方式，后端会从 MinIO 读取图片：

```text
QuickDetectionPhoto.storage_bucket
QuickDetectionPhoto.storage_object_key
  -> get_object_bytes(...)
  -> 得到图片 bytes
```

### 4.2 后端怎么请求模型服务

`reports.py` 中的 `_trial_inference_request` 会自己组装 multipart 请求体，然后用 Python 标准库 `urllib.request.urlopen` 调用模型服务：

```text
TRIAL_ALGORITHM_INFERENCE_URL=http://localhost:9004
POST {TRIAL_ALGORITHM_INFERENCE_URL}/predict
```

发送给模型服务的字段是：

```json
{
  "models": ["crack", "missing"],
  "high_precision": "false"
}
```

图片作为 multipart 的 `file` 字段发送。

这里没有额外引入 `requests` 依赖，原因是后端已有标准库实现就能满足当前需求。

### 4.3 模型类型转换

前端 trial 页面展示的是中文名称，例如：

```text
裂缝
面砖剥落
```

后端在调用模型服务前会转换为系统类型：

| 前端/请求值 | 系统类型 |
| --- | --- |
| `裂缝` | `crack` |
| `开裂` | `crack` |
| `面砖剥落` | `missing` |

转换后传给 `algorithm-model`，避免模型服务同时理解页面文案和业务文案。

### 4.4 推理结果怎么变成 trial findings

模型服务返回的是统一检测结果：

```json
{
  "image": {"width": 1920, "height": 1080},
  "detections": [
    {
      "id": "missing-1",
      "type": "missing",
      "confidence": 0.88,
      "bbox": {"x": 100, "y": 200, "width": 300, "height": 180}
    }
  ]
}
```

后端 `_trial_findings_from_inference` 会转换为前端 trial 页面需要的 finding：

```json
{
  "photo_id": "uuid",
  "filename": "photo.jpg",
  "model": "面砖剥落",
  "confidence": 0.88,
  "bbox": {"x": 100, "y": 200, "width": 300, "height": 180},
  "image_width": 1920,
  "image_height": 1080,
  "detection_id": "missing-1"
}
```

trial 后端还有一层兜底过滤：如果模型服务返回的 detection 没有合法置信度，或 `confidence < 0.6`，该 detection 会被直接跳过，不会返回给前端显示。

前端拿到 `bbox`、`image_width`、`image_height` 后，按当前图片展示尺寸计算百分比位置并叠框。这样即使图片在页面上缩放，检测框也能对齐。

### 4.5 模型不可用时的行为

当前 `.env` 中配置：

```env
TRIAL_ALGORITHM_INFERENCE_URL=http://localhost:9004
TRIAL_ALGORITHM_INFERENCE_TIMEOUT_SECONDS=120
```

如果模型服务没有配置、超时、返回 4xx/5xx，`/api/trial/generate` 会返回 503：

```text
简易检测模型服务不可用：...
```

当前简易体验不再降级为模拟结果，目的是确保验收到的就是 `wall-crack` 和 `missing` 真实模型输出。

## 5. 正式任务 Worker 如何接入真实模型

正式任务相关代码位于：

```text
backend/app/api/detection_tasks.py
backend/app/schemas/phase5.py
algorithm-worker/mock_worker.py
```

虽然文件名仍叫 `mock_worker.py`，但它已经同时支持两种模式：

| 模式 | 配置 | 行为 |
| --- | --- | --- |
| 模拟模式 | `WORKER_MODE=mock` | 下载图片后回传固定 JSON，用于验证后端任务契约 |
| 真实模式 | `WORKER_MODE=real` | 下载图片，调用 `algorithm-model /predict`，再回传真实检测结果 |

### 5.0 小白版执行顺序

正式项目检测可以理解成“后端发任务，Worker 干活，模型服务只负责识别图片”。

完整顺序如下：

1. 用户在前端项目详情页上传外墙照片。
2. 用户选择检测模型，例如 `crack`、`missing`。
3. 用户点击开始 AI 检测。
4. Web 后端创建一条检测任务，任务状态是 `pending`。
5. `algorithm-worker` 主动问后端：“有没有任务给我处理？”
6. 后端把一条 `pending` 任务锁给这个 Worker，任务状态变成 `running`。
7. 后端把照片下载地址、要跑的模型类型、是否高精度等信息返回给 Worker。
8. Worker 用后端返回的 `download_url` 下载图片。
9. Worker 把图片通过内部 API 发给 `algorithm-model /predict`。
10. `algorithm-model` 加载 `wall_crack_yolo11x.pt`、`missing.pt`，执行 YOLO 推理。
11. `algorithm-model` 返回 bbox、confidence、type 等检测结果。
12. Worker 把模型结果整理成后端要求的 JSON。
13. Worker 调后端 `/api/algorithm/tasks/{task_id}/results` 回传结果。
14. 后端校验结果合法后写入 `AiDetectionResult`。
15. 后端把任务状态改成 `success`，把项目状态改成 `pending_review`。
16. 审核工作台读取后端数据，展示 AI 检测框。

这条链路里有两个方向的 API 调用：

```text
Worker -> Web 后端
  用途：领取任务、发送心跳、回传结果、回传失败原因

Worker -> algorithm-model
  用途：把图片发给模型服务做推理
```

Web 后端不会在正式任务里主动调用 `algorithm-model`。这样即使模型跑得很慢、占用 GPU 或临时失败，也不会把 Web 后端进程拖住。

### 5.1 Worker 鉴权

Worker 调后端 API 时必须带两个请求头：

```http
X-Worker-Id: mock-worker-local
X-Worker-Token: change-this-worker-token
```

后端用 `WORKER_TOKEN` 校验 Token。`worker_id` 会写入任务锁，用来确保领取任务的 worker 才能 heartbeat、回传结果或标记失败。

### 5.2 领取任务

Worker 调用：

```http
GET /api/algorithm/tasks/next?model_version=trial-crack-missing-v1
```

后端会查找状态为 `pending` 的任务，并使用数据库 `FOR UPDATE SKIP LOCKED` 锁住一条任务，避免多个 worker 同时领取同一任务。

领取成功后，任务状态变为：

```text
pending -> running
```

后端返回的任务里包含：

```json
{
  "task_id": "uuid",
  "project_id": "uuid",
  "lease_expires_at": "2026-07-07T10:00:00Z",
  "models": ["crack", "missing"],
  "high_precision": false,
  "model_version": "trial-crack-missing-v1",
  "photos": [
    {
      "photo_id": "uuid",
      "original_filename": "photo.jpg",
      "download_url": "http://...",
      "storage_bucket": "building-exterior",
      "storage_object_key": "..."
    }
  ]
}
```

注意：`download_url` 是 MinIO 预签名地址，Worker 不需要 MinIO 写入密钥。

### 5.3 Worker 调模型服务

真实模式下，`build_real_results` 对每张照片执行：

```text
download_photo_bytes(photo)
  -> request_inference(photo, content, models, high_precision)
  -> normalize_detection(...)
```

`request_inference` 和 trial 后端类似，也是组装 multipart：

```text
POST {ALGORITHM_INFERENCE_URL}/predict
```

默认容器内地址：

```env
ALGORITHM_INFERENCE_URL=http://algorithm-model:9002
```

这就是 Worker 连接模型服务的内部 API 地址。它不是后端 API，也不是前端 API：

```text
http://algorithm-model:9002/predict
```

含义拆开看：

| 片段 | 含义 |
| --- | --- |
| `http://` | 普通 HTTP 请求 |
| `algorithm-model` | Docker Compose 服务名，Docker 内部 DNS 会把它解析到模型容器 |
| `9002` | 模型容器内部监听端口 |
| `/predict` | 模型推理接口 |

所以 Worker 在 Docker 里调用模型时，不需要知道宿主机 IP，也不需要通过 Nginx 或公网端口绕一圈。

发送字段：

```json
{
  "models": ["crack", "missing"],
  "high_precision": "false"
}
```

图片仍然作为 multipart 的 `file` 字段发送。

### 5.4 Worker 结果归一化

模型服务返回 `detections` 后，Worker 会做二次校验：

- `type` 必须能归一化为 `crack` 或 `missing`。
- `bbox` 必须存在且是对象。
- `confidence` 必须是合法数字。
- `type_name` 由 Worker 统一填成中文：`裂缝` 或 `面砖剥落`。
- `description` 为空时自动填成 `疑似裂缝。` 或 `疑似面砖剥落。`

Worker 不负责业务展示阈值。正式任务的 `confidence < 0.6` 过滤统一放在 Web 后端结果落库接口里，这样即使以后换了 Worker 或模型服务，低置信度结果也不会进入审核工作台和报告。

最终回传给后端的结构是：

```json
{
  "task_id": "uuid",
  "project_id": "uuid",
  "model_version": "trial-crack-missing-v1",
  "started_at": "2026-07-07T10:00:00Z",
  "finished_at": "2026-07-07T10:01:00Z",
  "results": [
    {
      "photo_id": "uuid",
      "detections": [
        {
          "id": "crack-1",
          "type": "crack",
          "type_name": "裂缝",
          "confidence": 0.91,
          "bbox": {
            "x": 120,
            "y": 80,
            "width": 260,
            "height": 140
          },
          "mask": null,
          "severity": null,
          "description": "疑似裂缝。"
        }
      ]
    }
  ]
}
```

### 5.5 后端怎么落库

Worker 调用：

```http
POST /api/algorithm/tasks/{task_id}/results
```

后端校验：

- 当前 worker 是否拥有该任务。
- payload 里的 `task_id`、`project_id` 是否和任务一致。
- 任务状态是否仍是 `running`。
- 回传的 `photo_id` 是否属于该任务。
- `type` 是否是系统枚举。
- `confidence` 是否在 `0-1`。
- `confidence` 是否大于等于业务展示阈值 `0.6`；低于 `0.6` 的 detection 会被跳过，不写入 `AiDetectionResult`。
- `bbox.x`、`bbox.y` 是否大于等于 0。
- `bbox.width`、`bbox.height` 是否大于 0。

校验通过后，后端会：

1. 删除该任务旧的 `AiDetectionResult`，避免重复写入。
2. 为每个 detection 创建新的 `AiDetectionResult`。
3. 将原始 detection 保存到 `raw_result_json`。
4. 将任务状态改为 `success`。
5. 统计 `result_summary.total_detections` 和 `by_defect_type`。
6. 将项目状态改为 `pending_review`。

如果 Worker 失败，会调用：

```http
POST /api/algorithm/tasks/{task_id}/failed
```

后端会把任务标记为 `failed`，把项目退回 `draft`，并保存失败原因。

### 5.6 心跳和租约

Worker 领取任务后，后端会设置租约过期时间：

```env
WORKER_LEASE_SECONDS=600
```

Worker 可以调用：

```http
POST /api/algorithm/tasks/{task_id}/heartbeat
```

心跳会刷新：

```text
worker_heartbeat_at
lease_expires_at
```

如果后续大批量图片或模型耗时较长，真实 Worker 应该在每张图或每个批次后发送 heartbeat，避免任务长时间无心跳。

## 6. 配置项说明

### 6.1 模型服务配置

```env
MODEL_DEVICE=auto
MODEL_VERSION=trial-crack-missing-v1
MODEL_DIR=./models
CRACK_MODEL_WEIGHTS_PATH=/models/wall_crack_yolo11x.pt
MISSING_MODEL_WEIGHTS_PATH=/models/missing.pt
MODEL_CONFIDENCE_THRESHOLD=0.25
MODEL_IMAGE_SIZE=1280
MODEL_HIGH_PRECISION_IMAGE_SIZE=1280
ALGORITHM_MODEL_PORT=9004
```

说明：

- `MODEL_DEVICE=auto` 时，有 CUDA 就使用 GPU 0，否则使用 CPU。
- `MODEL_CONFIDENCE_THRESHOLD` 会同时传给 YOLO `conf` 参数，并在模型服务解析结果时再次过滤。当前默认值是 `0.25`，它是模型原始输出的基础阈值，不是业务展示阈值。
- 业务展示和正式落库阈值是 `0.6`，由 Web 后端控制。trial 后端会过滤 `confidence < 0.6` 的 finding；正式任务结果接口会过滤 `confidence < 0.6` 的 detection，低置信度框不会进入审核工作台或报告。
- `MODEL_IMAGE_SIZE` 是普通检测输入尺寸。
- `MODEL_HIGH_PRECISION_IMAGE_SIZE` 是高精度模式输入尺寸，当前默认也为 1280。
- `ALGORITHM_MODEL_PORT=9004` 是宿主机访问端口；容器内服务端口固定为 9002。

### 6.2 trial 调用配置

```env
TRIAL_ALGORITHM_INFERENCE_URL=http://localhost:9004
TRIAL_ALGORITHM_INFERENCE_TIMEOUT_SECONDS=120
```

trial 后端运行在宿主机或本地 Python 进程中，所以访问模型服务用宿主机端口 `9004`。

### 6.3 Worker 调用配置

```env
WORKER_BACKEND_BASE_URL=http://localhost:8000
WORKER_CONTAINER_BACKEND_BASE_URL=http://host.docker.internal
WORKER_ID=mock-worker-local
WORKER_TOKEN=change-this-worker-token
WORKER_MODEL_VERSION=trial-crack-missing-v1
WORKER_MODE=mock
WORKER_LEASE_SECONDS=600
ALGORITHM_INFERENCE_URL=http://algorithm-model:9002
ALGORITHM_INFERENCE_TIMEOUT_SECONDS=120
```

如果在 Docker Compose 内运行 Worker，Worker 访问模型服务使用 Docker 内部服务名：

```text
http://algorithm-model:9002
```

如果在宿主机直接运行 Worker，需要把 `ALGORITHM_INFERENCE_URL` 改成：

```env
ALGORITHM_INFERENCE_URL=http://localhost:9004
```

### 6.4 内部地址和外部地址怎么选

最容易配错的是模型服务地址。判断规则很简单：看“发起请求的程序”运行在哪里。

| 发起请求的程序 | 运行位置 | 应该使用的地址 | 原因 |
| --- | --- | --- | --- |
| 后端 trial 接口 | 宿主机 Python 进程 | `http://localhost:9004` | 宿主机通过端口映射访问模型容器 |
| Worker | Docker Compose 容器内 | `http://algorithm-model:9002` | 同一 Docker 网络内通过服务名访问容器内部端口 |
| Worker | 宿主机 Python 进程 | `http://localhost:9004` | 宿主机不能解析 Docker 服务名，应该走端口映射 |
| 浏览器用户 | 外部浏览器 | 不直接访问模型服务 | 模型服务不面向普通用户开放 |

两个地址对应的是同一个模型服务，只是访问入口不同：

```text
Docker 内部访问：
algorithm-worker 容器 -> http://algorithm-model:9002 -> algorithm-model 容器

宿主机访问：
后端本地进程或 curl -> http://localhost:9004 -> Docker 端口映射 -> algorithm-model 容器 9002
```

因此：

- `TRIAL_ALGORITHM_INFERENCE_URL` 通常写 `http://localhost:9004`。
- Docker 里的 `ALGORITHM_INFERENCE_URL` 通常写 `http://algorithm-model:9002`。
- 宿主机直接运行 Worker 时，`ALGORITHM_INFERENCE_URL` 改为 `http://localhost:9004`。
- 不要让前端浏览器直接请求 `algorithm-model`，前端只调用 Web 后端 API。

## 8. 新增模型时怎么扩展

当前真实接入只覆盖 `crack` 和 `missing`。如果后续新增 `spalling`、`moisture` 等模型，建议按下面顺序处理。

### 8.1 增加系统枚举和页面配置

先确认后端、数据库、前端是否已经支持对应缺陷类型。当前系统枚举里保留了：

```text
crack
missing
spalling
moisture
```

但真实模型服务目前只执行 `crack` 和 `missing`。

### 8.2 增加权重配置

如果继续采用一个缺陷类型一个 YOLO 权重的方式，需要在模型服务里增加：

```text
DEFECT_CLASS_ORDER
DEFECT_LABELS
DEFAULT_MODEL_PATHS
CLASS_ALIASES
```

并在 `.env` 和 `docker-compose.yml` 增加对应权重路径。

如果采用 `MODEL_WEIGHTS_CONFIG`，也要确保 `_configured_model_paths` 能识别新增类型。

### 8.3 确认模型输出

新增模型前需要算法侧明确：

```text
模型权重文件名
模型类别 id
模型类别名
类别名到系统枚举的映射
推荐 conf
推荐 imgsz
是否需要单独 iou、half、device、batch 参数
输出是 bbox、mask 还是 polygon
坐标是否基于原图
```

当前系统主要处理 bbox。如果后续输出 mask 或 polygon，需要扩展后端表结构、审核页面和报告展示。

### 8.4 更新 Worker 和 trial 映射

新增类型后至少要同步更新：

```text
backend/app/api/reports.py
algorithm-worker/mock_worker.py
algorithm-model/server.py
frontend/src/types/projects.ts
相关页面展示和颜色配置
```

否则会出现模型服务能返回结果，但后端或前端不认该类型的情况。

## 10. 常见问题

### 10.1 `/ready` 返回 `ready: false`

优先检查：

```bash
ls -lh models/wall_crack_yolo11x.pt models/missing.pt
docker compose --profile algorithm-gpu exec algorithm-model ls -lh /models
docker compose --profile algorithm-gpu exec algorithm-model python verify_environment.py
```

常见原因：

- 权重没有放到 `models` 目录。
- 宿主机路径挂载错。
- `.env` 中权重路径写错。
- 权重文件损坏或和当前 Ultralytics 版本不兼容。

### 10.2 GPU 不可用

检查：

```bash
nvidia-smi
docker run --rm --gpus all nvidia/cuda:12.9.0-base-ubuntu22.04 nvidia-smi
docker compose --profile algorithm-gpu config
```

如果 `torch.cuda.is_available()` 是 `false`，先处理 NVIDIA 驱动、NVIDIA Container Toolkit 和 Docker GPU 配置。临时验证可以设置 `MODEL_DEVICE=cpu`。

### 10.3 OpenCV 或 libGL 报错

模型容器使用无头环境，应该使用 `ultralytics-opencv-headless`，不要混装 `opencv-python` 和 `opencv-python-headless`。

### 10.4 Worker 下载不到图片

检查 MinIO 对外地址：

```env
MINIO_ENDPOINT=服务器IP:9002
MINIO_PUBLIC_URL=http://服务器IP:9002
```

正式环境不要保留 `localhost:9002` 作为预签名 URL 的公开地址，否则 Worker 容器或其他机器访问不到。

### 10.5 bbox 在前端位置不对

检查三件事：

1. 模型服务返回的 bbox 是否是原图坐标。
2. 返回的 `image.width`、`image.height` 是否和原图一致。
3. 前端叠框是否使用原图尺寸做比例换算，而不是直接使用页面显示像素。

### 10.6 正式任务结果回传失败

常见原因：

- Worker Header 中的 `X-Worker-Token` 和后端 `.env` 的 `WORKER_TOKEN` 不一致。
- 任务已经被另一个 worker 领取，当前 worker 不是 owner。
- `payload.task_id` 或 `payload.project_id` 和任务不匹配。
- 回传了任务外的 `photo_id`。
- `type` 不是系统枚举。
- `bbox.width` 或 `bbox.height` 小于等于 0。
- `confidence` 不在 `0-1`。

## 11. 推荐交付顺序

1. 确认 `models/wall_crack_yolo11x.pt` 和 `models/missing.pt` 是当前要验收的权重。
2. 构建并启动 `algorithm-model`。
3. 用 `/ready` 验证两份权重能加载。
4. 用 `/predict` 直接验证单张图片推理输出。
5. 用 `/trial` 验证简易体验页面展示真实检测框。
6. 将 Worker 切换为 `WORKER_MODE=real`。
7. 创建正式项目、上传图片、选择 `crack` 和 `missing`。
8. 启动检测任务，确认 Worker 领取、下载、推理、回传。
9. 检查 `AiDetectionResult`、审核工作台、报告详情是否正确展示。
10. 固化模型版本号、置信度阈值、输入尺寸和部署命令。
